1

📥 /ingere: um link novo, o mentor inteiro atualizado

O especialista publicou um guia novo. Você não recompila a wiki inteira nem reescreve regras à mão: roda /<slug>-ingere <link>. A skill coleta, cria a página da fonte, propaga pelas páginas afetadas, mexe nas regras se for o caso, registra no log e prova com os três validadores.

Novo aqui? Ingestão e propagação

Ingestão é colocar uma fonte nova para dentro do mentor. Propagar é atualizar toda página da wiki que esse conteúdo toca — tema, princípio, método — com link nos dois sentidos. Sem propagar, a fonte nova fica isolada e o mentor nunca a usa.

Como ler: a fila rosa é o caminho normal; o desvio ciano à esquerda é a trava contra duplicação, e o da direita é a última coisa que o aluno vê. O cartão brilhante é o que torna a ingestão confiável: sem os três exit 0, não terminou.

O caso real: um guia sobre usar dois agentes

🧪 Faça agora — ingerir um conteúdo novo do seu especialista

Objetivo: fazer o teste 3 no seu mentor e conferir por fora. Commit antes, para ver exatamente o que a ingestão mudou.

cd ~/mentores/mentor-<slug>
git add -A && git commit -qm "antes da ingestão"
claude
# dentro do Claude Code:
/<slug>-ingere <link novo do especialista, fora do ESCOPO.md>
# de volta ao terminal:
tail -1 wiki/log.md
git status --short wiki/ regras.md
python3 tools/stats.py && python3 tools/validar_links.py && python3 tools/validar_citacoes.py; echo "exit=$?"

Como verificar: a última linha do log tem a data e a fonte nova; o git status mostra uma página nova em wiki/fontes/ e páginas modificadas; exit=0 no fim. Se o git status mostrar algo em raw/ que não seja o item novo, a ingestão mexeu no acervo cru: anote no diário.

2

🎖️ Promoção de regras: banco → ativa

Na trilha 4 você viu os três status de uma regra. A ingestão é o momento em que eles se movem. Uma regra com uma fonte só fica no banco, esperando; quando chega a 2ª fonte diferente dizendo a mesma coisa, ela é promovida a ativa e passa a guiar o mentor.

Como ler: só a seta rosa do meio muda o status — e ela exige uma 2ª fonte diferente. A volta à direita mostra o reforço, que não muda o status, só engrossa a prova. A inferência fica de lado, tracejada: é útil, mas nunca finge ter fonte.

No piloto aconteceu um caso curioso: R9 e R10 nasceram já ativas. O comportamento era novo no guia ingerido, mas a 2ª fonte já estava no acervo cru, dizendo o mesmo sem que ninguém tivesse transformado aquilo em regra — uma live, no caso da R9, e outro guia, no da R10. Veja a R9 como ficou: 

## R9 — Revisar com outro agente, entregando o artefato real
- status: ativa
- enunciado: Pôr uma segunda IA para questionar e testar o que a primeira fez, dando a ela o mesmo
  briefing e o arquivo, diff ou saída de teste (nunca um resumo), e não tratar a concordância das
  duas como prova.
- citacoes:
  - "também é muito bom tu ter uma outra IA" — raw/videos/inema-vibecode-do-zero-dia-1-…txt@00:08:29
  - "dê ao segundo agente o mesmo briefing da tarefa e o artefato real" — raw/guia/agente-claude-codex-…md
  - "Os dois concordarem não é prova: eles podem dividir a mesma suposição errada." — raw/guia/agente-claude-codex-…md
- no mentor: seção Revisão — o mentor pede o artefato (arquivo, diff, saída) em vez da descrição…

R9 — Revisão cruzada

Fontes: uma live (vídeo) + o guia novo. Repare como ela ecoa o módulo 6.1: entregar o artefato real, não o resumo — o mesmo motivo de o validador ler o log e não o relato.

R10 — Handoff não é permissão

Gasto, publicação, deploy, envio ou apagar viram portão humano; nota antiga ou plano não autorizam. Fontes: dois guias diferentes. No mentor, vira a seção Risco.

🧪 Faça agora — o que a ingestão fez com as suas regras

Objetivo: contar regras por status antes e depois, e ver exatamente qual linha mudou.

cd ~/mentores/mentor-<slug>
git show HEAD:regras.md | grep -E '^- status:' | sort | uniq -c   # antes (último commit)
grep -E '^- status:' regras.md | sort | uniq -c                   # agora
git diff --word-diff regras.md | grep -E 'status|^## R'

Como verificar: se uma regra passou de banco para ativa, ela precisa ter agora 2 citações de arquivos diferentes do raw/. Confira com python3 tools/validar_citacoes.py → exit 0. Se nenhuma mudou, tudo bem: a fonte só reforçou ou não tocou regras.

3

🔄 novo-mentor.py --atualizar

O kit evolui — o 1.2 nasceu do piloto. Seu mentor já existe, com acervo, wiki e regras que custaram horas. Gerar de novo seria perder tudo. O --atualizar faz a separação: troca o que é código e instrução do kit e não encosta no que é conteúdo seu.

✓ O que ele atualiza

  • ✓tools/ — coletores e validadores
  • ✓.claude/ — agente, skills, hooks e settings
  • ✓material dos testes: README.md, script_emoji.py, comentarios.json
  • ✓mentor.config.json: só acrescenta chaves novas; nunca sobrescreve as suas

✗ O que ele não toca

  • ✗raw/ — o acervo cru
  • ✗wiki/ e regras.md
  • ✗ESCOPO.md e CLAUDE.md
  • ✗testes/respostas/ — as respostas que você guardou

💡 E se eu personalizei o agente?

Cada arquivo que vai ser trocado e estava diferente do novo é copiado antes para .mentor/backup-<data>/. O comando avisa no fim: "se você tinha personalizado o agente, compare". No piloto, a atualização para o 1.2 mexeu em 9 arquivos — agente, 3 skills, config e 4 tools — e nenhuma página da wiki.

🧪 Faça agora — atualizar o seu mentor com segurança

Objetivo: levar seu mentor para a versão atual do kit e provar que o conteúdo não mudou.

cd ~/caminho/do/kit/mentor-especialista && git pull && cat VERSION
cd ~/mentores/mentor-<slug> && git add -A && git commit -qm "antes de atualizar o kit"
python3 ~/caminho/do/kit/mentor-especialista/novo-mentor.py --atualizar ~/mentores/mentor-<slug>
git status --short | grep -E ' (raw|wiki)/| regras.md| ESCOPO.md' || echo "conteúdo intacto"
python3 tools/stats.py && python3 tools/validar_links.py && python3 tools/validar_citacoes.py; echo "exit=$?"

Como verificar: a saída do --atualizar termina com "Não mexi em: raw/, wiki/, regras.md, ESCOPO.md, CLAUDE.md, testes/respostas/."; o grep imprime "conteúdo intacto"; os validadores dão exit=0. Depois rode de novo o teste 2 do módulo 6.1 para ver se a versão nova mudou o placar.

4

♻️ Reuso para outro especialista

Nada no kit é específico do Nei. O que muda de um especialista para outro é o conteúdo — acervo, wiki, regras — e, às vezes, o formato da resposta. O núcleo (raw/, wiki/, regras.md, tools/) nem depende do Claude Code.

Três tipos de reuso

Mesmo tipo de domínio (ensina código)

Rode o novo-mentor.py de novo com outro slug, nome e domínio. Repita as fases 1–5. Calibre as metas depois de listar as fontes — no piloto, a meta de guias reprovou porque cada guia tinha 900–1.400 palavras.

Domínio que não é código (vendas, escrita, coaching)

Troque o loop no agente e as secoes_resposta no config. O portão continua lá; se o mentor nunca gerar script, ele simplesmente nunca bloqueia.

Outro agente (fora do Claude Code)

Copie o corpo do agente para o arquivo de instruções do outro agente (ex.: AGENTS.md) e transforme cada skill em comando salvo. Sem hooks, não há portão: rode validar_resposta.py --transcript depois de cada resposta — a verificação de fora do módulo 6.1 vira a sua única garantia.

Exemplo de seções para um mentor de escrita, no mentor.config.json:

"secoes_resposta": ["Objetivo", "Rascunho mínimo", "Previsão de reação", "Teste com leitor", "Versão fraca", "Relatório"]

⚠️ O que não muda de um mentor para outro

Copiar o método, nunca a voz nem a identidade (trilha 1). Toda regra ativa com 2 fontes reais. Os 3 testes antes de usar. Mudar de especialista não é desculpa para pular a prova.

🧪 Faça agora — o segundo mentor

Objetivo: gerar o esqueleto de um segundo mentor ao lado do primeiro, sem misturar os dois.

cd ~/caminho/do/kit/mentor-especialista
python3 novo-mentor.py <slug2> --nome "<Nome do 2º especialista>" \
  --dominio "<domínio numa frase estreita>" --destino ~/mentores
ls ~/mentores
ls ~/mentores/mentor-<slug2>/.claude/skills

Como verificar: ~/mentores lista as duas pastas; o novo tem 6 skills com o prefixo <slug2>-. Se você rodar de novo com o mesmo slug, o gerador recusa ("já existe") — ele não sobrescreve um mentor sem --forcar.

5

🏛️ Conselho de mentores

Com dois ou mais mentores prontos, você pode juntá-los num projeto seu e consultar todos sobre a mesma pergunta. Cada um continua preso às próprias regras e citações: o conselho não mistura as vozes, compara os métodos.

Novo aqui? Subagente

Um subagente é um assistente especializado que o Claude Code chama para uma tarefa, com instruções próprias, definido num arquivo em .claude/agents/. Cada mentor tem o seu (<slug>-mentor.md). Juntar os arquivos numa pasta só deixa a sessão chamar qualquer um deles.

Como ler: a pergunta se divide em dois caminhos independentes (rosa e ciano) que só se encontram na comparação. O valor está na divergência: onde os dois concordam, a R9 lembra que isso não é prova — eles podem dividir a mesma suposição errada.

🧪 Faça agora — montar e consultar o conselho

Objetivo: juntar os agentes de dois mentores num projeto e fazer uma pergunta aos dois.

mkdir -p ~/projetos/<meu-projeto>/.claude/agents
cp ~/mentores/mentor-<slugA>/.claude/agents/<slugA>-mentor.md ~/projetos/<meu-projeto>/.claude/agents/
cp ~/mentores/mentor-<slugB>/.claude/agents/<slugB>-mentor.md ~/projetos/<meu-projeto>/.claude/agents/
cd ~/projetos/<meu-projeto> && claude

# prompt para colar na sessão:
Consulte o subagente <slugA>-mentor e o subagente <slugB>-mentor, separadamente,
sobre: <sua pergunta>. Entregue aos dois o arquivo <caminho do artefato>, não um resumo.
Avise cada um de onde está o próprio núcleo: o <slugA>-mentor usa regras.md e wiki/
em ~/mentores/mentor-<slugA>/; o <slugB>-mentor, em ~/mentores/mentor-<slugB>/.
Depois compare numa tabela: onde concordam, onde divergem e qual regra (R1, R2…) de
cada um justificou a posição. Não escolha um vencedor: a decisão é minha.

Como verificar: a tabela cita IDs de regra de cada mentor. Abra o regras.md de cada um e confira se esses IDs existem e dizem o que a tabela afirma. Por que avisar o caminho: o agente procura regras.md e wiki/ como caminhos relativos, e no seu projeto eles não existem. Se a tabela vier sem regras, o subagente não achou o núcleo e está respondendo genérico.

🎓 Projeto final e rubrica

O projeto final é o mentor completo de um especialista à sua escolha — você mesmo é uma opção forte. O acervo do curso é menor que o do piloto de propósito: 20 a 50 fontes, cerca de 50 mil palavras. Um acervo completo é caro demais para exercício.

🧪 Faça agora — a autoavaliação por comando

Objetivo: conferir os itens automáticos da rubrica de uma vez. Os itens de demonstração (portão e ingestão) você grava ou printa.

cd ~/mentores/mentor-<slug>
for t in stats validar_links validar_citacoes; do
  python3 tools/$t.py >/dev/null 2>&1 && echo "ok   $t" || echo "FALHA $t"
done
python3 tools/validar_resposta.py testes/respostas/<arquivo do teste 1>.md \
  --transcript logs/teste1.jsonl >/dev/null && echo "ok   loop" || echo "FALHA loop"
grep -c '^| 20' testes/aceitacao/RESULTADOS.md     # linhas de resultado registradas
tail -1 wiki/log.md

Como verificar: quatro linhas "ok" valem até 6 pontos; o grep deve contar ao menos 3 linhas; a última do log deve ser a sua ingestão. Some com as demonstrações. Abaixo de 8, volte ao módulo do critério que falhou — a mensagem do validador diz qual é.
